# 安全模型

在转换和验证成功之前，MyVidComp 绝不替换源视频；在最终提交之前，绝不触及目标文件夹。

## 临时文件

- 长时间运行的 ffmpeg 写入进入 MyVidComp 自有的临时文件，命名 `.myvidcomp-<stem>-<timestamp>.tmp.mp4` 或 `.tmp.mkv`。
- 配置 `tmp_dir` 时，临时文件位于该本地目录（对 SMB/NAS 目标有用）；否则位于源文件旁。
- 缓存的临时输出只按精确名称识别：`.myvidcomp-<stem>-<数字>.tmp.mp4` 或 `.tmp.mkv`（或旧版 `.pvac-` 前缀），因此 `clip` 绝不会认领 `clip-b` 的临时输出，`.repairing` 残留也不会被当作已完成的临时输出。
- 缓存的临时输出只有在同一验证路径通过后才可复用——绝不仅因文件存在——按本次运行要求的编解码器检查，时长容差比新编码严格十倍（见 [validation.md](validation.md)）。复用的临时输出仍会被测量，也仍可能进入复核。
- 中途停止的元数据修复留下的 `.repairing` 旧文件会在下一次修复开始前被删除，因此不会永远阻止该临时输出的修复。
- 不可读的 MyVidComp 临时输出，尤其是无可读视频流或编解码器错误的文件，会被删除且不复用。只有匹配 MyVidComp 临时命名的文件才会被删除。
- 若引擎失去对运行中 ffmpeg 的掌控（无法再读取其进度），会先终止并回收该 ffmpeg 再报告错误，因此不会有孤儿进程继续写入临时文件。

## 编码前的冲突检测

当输出路径、`.old` 路径、临时路径或 `.myvidcomp.recover` 路径已存在时，文件以冲突原因跳过。已存在的输出文件和 `.old` 文件绝不静默覆盖。

输出名称与源仅大小写不同时（`clip.MP4` 变为 `clip.mp4`），若两个名称是同一个文件（在不区分大小写的磁盘上即如此），不算冲突。两条路径只有在都存在、都不是符号链接，并且（在 Linux、macOS 和 Android 上）设备号与 inode 相同且只有一个链接，或（在 Windows 上）解析为同一完整路径时，才算同一文件。在区分大小写的磁盘上，`clip.MP4` 旁另有一个 `clip.mp4` 仍是冲突。

## 提交

- 提交仅在完整验证通过后发生。
- 验证通过的临时输出通过同目录重命名替换源文件；跨设备移动回退为带进度的复制。
- 使用 `--keep-original` 时，原始文件先改名为 `<name>.<ext>.old`。
- 最终提交临时路径位于目标旁，使最后一次重命名同卷。
- 恢复路径命名（`.myvidcomp.recover`）支持中断提交的人工恢复。
- 输出名称就是源文件本身时（包括 `clip.MP4` 对应的大小写不同的 `clip.mp4`），通过恢复重命名提交：源文件先改为恢复名称，转换结果接管输出名称，之后才删除恢复副本。两个名称是否为同一文件在任何移动之前判断，因为源文件改名后就无法再看到它；把两个名称当作不同文件，会在写入转换结果后立刻把它删除。
- 复制回退中途失败时，会删除不完整的暂存文件。

## 原始文件

测试绝不覆盖、删除或改名真实用户视频——测试使用合成夹具。在转换和验证成功之前，原始文件始终保留。

## 优雅停止

- CLI：输入 `q` 回车，再以 `y` 确认。
- 确认提示激活期间暂停进度刷新。
- 活动的 ffmpeg 进程绝不中断；MyVidComp 完成当前文件后，在开始下一个文件前停止。
- 嵌入 API 通过 `CancellationToken::request_stop` 取消，语义相同。

## 配置

`config.yaml` 是用户所有的输入：MyVidComp 按需读取，但从不重写或规范化它。GUI 将自身偏好存储在用户配置目录，且不得重写 `config.yaml`。
