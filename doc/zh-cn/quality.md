# 画质

MyVidComp 如何决定转换结果应该是什么样，以及如何检查是否达到了这个目标。

## 测量什么

画质用 VMAF 测量，这是 Netflix 基于真人评分训练出来的模型。它把转换后的文件与源做比较，给出一个
0 到 100 的数字。大约 6 分相当于一个「刚好能察觉的差异」，而 93 到 95 分左右是大多数观众再也分不
出两者区别的位置。这就是默认目标定在 95 的原因。

分数在程序内部一律以百分之一为单位保存，因此跨越嵌入边界时都是整数。

## 测量方式

测量运行 FFmpeg 的 `libvmaf` 滤镜，第一个输入是转换后的文件，第二个是源。顺序很重要：反过来仍然
会得出一个数字，只是另一个数字。

每次比较都会做三件事：

- 两个输入都转换成同一种平面 YUV 格式，因为该滤镜会拒绝格式、宽度或高度不一致的输入。格式根据源
  自身的色度布局和位深选择。
- 两个输入的时间基和起始时间都会重置。否则不从零开始的源分数会低得离谱，因为滤镜比对的是错位的帧。
- 解码可以交给显卡，但比对本身永远在处理器上进行。两个文件分别解码，因为它们的编码不同，
  能读其中一个的硬件未必能读另一个；解出的帧会被取回普通内存交给滤镜。

模型按分辨率选择：1440p 以上用 4K 模型，以下用标准模型。

FFmpeg 中 `n_threads` 默认只用一个线程，对整片来说太慢，因此除非另行指定，MyVidComp 会把它设为
核心数。

## 何时不准

已发布的 VMAF 模型是基于标准动态范围视频训练的。HDR 源仍会评分，但结果会附带一条说明，指出该分数
仅供参考，不应仅凭它否定一次 HDR 转换。

## 选择设置

编码器对同一个画质数字的理解并不一致，同一个数字在不同素材上的表现也不同。有两种选定方式。

### 实测并调整

从源中不重新编码地复制出短片段，分布在文件中段，避开片头和片尾。每十二分钟取一段，每段二十秒，
最多六段。

每次试编码用一个设置编码全部片段，并逐帧测量结果，然后向刚好高于目标的设置插值逼近。当区间收窄到
一步、出现重复设置，或试到第六次时，搜索结束。最终选择通过目标的最大值，也就是仍能达到目标的最小
文件。

如果没有任何设置达到目标，就采用最好的一次，并明确说明。

试编码使用各编码器最快的预设。预设对文件大小的影响远大于对画质的影响，因此试编码的分数仍足以预测
最终结果，可以据此引导搜索。

显卡编码器没有可用的恒定画质控制，因此改为按码率阶梯搜索：源码率的 15%、25%、40%、60% 和 85%，
在第一个达到目标的档位停下。

## 快速估算

设置由源自身的编码器元数据推算得出，没有元数据时则按每像素每帧的码率推算，再换算到目标编码器的
标度上。它不花任何额外时间，精度也较低。短于 90 秒的文件一律使用它。

## 转换之后

除非关闭画质检查，每次完成的转换都会与源比较；而改动了可恢复细节的转换无论如何都会比较。

结果不低于「目标减去复核余量」时正常提交。低于该值时会连同分数一起保留在原文件旁边，交由用户决定。
参见 [review.md](review.md)。

上一次中断留下的缓存工作文件同样会被测量，因此复用它绝不会跳过检查。

## 代价

测量并不免费。逐帧比较一个 1080p 文件所花的时间与编码它差不多，4K 还要糟糕数倍。抽样检查每五帧
比对一帧，快上数倍，精度也足以据此决定。调整搜索会在此之上再加几次短编码。

## 读取视频的方式

每个文件都要解码两次：一次用于转换，一次用于把结果和源作比较。`--decoder` 设置决定这些解码发生
在哪里。

默认的 `auto` 会在确认显卡可用时使用显卡。确认分两步，因为二者回答的不是同一个问题：创建设备说
明驱动是否存在，而解码真实文件的两帧才说明这种编码到底受不受支持。没有 AV1 解码器的硬件能完美
处理 H.265 却会拒绝 AV1；结论按编码记住，所以同一种编码的一整个文件夹只问一次。

正式工作中出现的任何失败都按同样的方式处理：给出一条警告，把这次工作放到处理器上重做，并且本次
运行不再使用显卡。这样一来，一次崩溃最多损失一次编码，而不是整个文件。这也是 `auto` 可以放心默
认开启的原因；早先的版本让 FFmpeg 自行挑选方式，结果大约每六次运行就崩溃一次。

`cpu` 永远不使用显卡。需要在另一台机器上得到同样的分数时，就选它。`gpu` 会优先要求显卡，用不了
时明确说明。写成 `d3d11va`、`cuda`、`vaapi` 或 `videotoolbox` 这样的方式名，则只用这一种。

被加速的是读取视频，而不是测量本身：VMAF 在任何情况下都跑在处理器上。即便如此，对 4K 文件仍然
有意义，因为这让处理器腾出手来做比对。

### 在显卡上测量

FFmpeg 还有第二个比对滤镜 `libvmaf_cuda`，它让画面从解码到打分全程留在 NVIDIA 显卡上。当这个滤镜
存在、源是 8 位 4:2:0，并且明确指定了 `--decoder cuda` 时，MyVidComp 会使用它。它绝不会被自动选
中，因为 MyVidComp 能用来测试的构建里都没有它。

任何人分发的构建里都没有它，这是许可证造成的门槛，而不是疏忽。这个滤镜需要用 CUDA 编译的 libvmaf，
并且 FFmpeg 要这样配置：

```sh
./configure --enable-nonfree --enable-ffnvcodec --enable-libvmaf
```

`--enable-nonfree` 产出的二进制不允许再分发，所以无论是 MyVidComp 捆绑其构建的 BtbN，还是
MyVidComp 自己，都无法把它交给别人。自己编译在 Linux 上可行；在 Windows 上则仍是个悬而未决的问题，
没有公开的做法。

因此对 NVIDIA 机器来说，真正有用的设置是 `--decoder cuda`：它今天就能配合捆绑的 FFmpeg 工作，把解
码而不是打分从处理器上挪走。如果你自己有带 CUDA 滤镜的构建，用 `--ffmpeg` 指向它即可，MyVidComp
会发现并说明。
