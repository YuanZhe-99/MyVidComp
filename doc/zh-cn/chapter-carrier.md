# QuickTime 章节承载轨处理

一些 MP4/MOV 源在专用数据轨中承载章节元数据——通常是 FourCC 为 `text` 的 `bin_data` 流——音视频轨通过 `tref/chap` 轨道引用指向它。FFmpeg 无法将这种轨复制进 MP4（会被改写为不相关的 `gpmd` 风格标签），也无法复制进 Matroska；且绝不能仅凭编解码器名就静默丢弃。MyVidComp 基于证据处理它。

## 候选条件

一条流是可能的章节承载轨，仅当**以下全部**成立：

- `codec_type` 为 `data` 且 `codec_name` 为 `bin_data`
- `codec_tag_string` 为 `text`
- 具有数字轨道 ID（`id` 按十进制或 `0x` 十六进制解析）

其他一切——`timed_id3`、附件、遥测、未知流——绝不按承载轨对待，进入普通容器选择路径。

## 确认：有界 ISO BMFF 读取

对存在承载轨候选的文件，MyVidComp 使用有界的、纯标准库的读取器读取源的 ISO BMFF 结构，收集被 `tref/chap` 显式指向的轨道 ID：

- 仅读取 `moov/trak/tkhd/tref/chap` 的 box 头；**绝不读取 `mdat`**，绝不加载媒体负载。
- 支持普通 32 位大小、扩展 64 位大小和父级结尾的 `size = 0` box。
- 每个 box 均按父级边界和全局 box 计数预算校验。
- 读取 `tkhd` 轨道 ID（版本 0 与 1）和 `chap` 目标 ID 列表。

当流的探测轨道 ID 被 `tref/chap` 指向时，它是**已确认的承载轨**。解析器是严格的：畸形或模糊的原子、多个 `moov`/`tkhd` box、零或非法目标 ID、预算溢出都会产生具体的逐文件跳过——绝不静默丢弃，绝不放中止整个批次。

## 已确认承载轨的策略

原始承载轨被排除出映射流和期望流签名。随后按探测到的章节元数据处理章节：

| 情况 | 策略 | FFmpeg | 验证 |
|---|---|---|---|
| 有效章节 | `ConfirmedMeaningful` | `-map_chapters 0` | 数量、时间戳（0.05 秒容差）、精确标题 |
| 空或单个无标题全片占位章节 | `ConfirmedEmpty` | `-map_chapters -1` | 无章节存在 |
| 普通源（无承载轨） | `Ordinary` | `-map_chapters -1` | 无（不强制章节映射） |

占位检测：章节列表为空，或恰好一个章节，其标题为空/空白、起点在 0.05 秒以内、终点与源时长之差在 `max(0.1 s, duration × 0.001)` 以内。此容差吸收实际封装器的时间戳改写。

有效章节在编码后做语义验证：章节数量、起点/终点时间戳（带容差）和精确标题文本。不完整或畸形的 ffprobe 章节记录（时间戳缺失或倒置）产生具体的逐文件跳过，而非被误判为空占位。

## 与其他策略的交互

- 承载轨排除发生在**容器选择之前**，因此已确认的承载轨绝不触发 MKV 回退；文件保持 MP4。
- 元数据修复重封装会探测自己的输入，并应用相同的章节策略和相同的实际索引映射。
- 一个文件存在多个已确认承载轨属于歧义，产生具体的安全跳过。
- 普通源保持不强制章节策略——章节绝不基于猜测映射。
